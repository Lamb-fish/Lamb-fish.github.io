TLCP 协议、套件与双证书

一、协议定位与标准

SSL VPN、TLS、TLCP 的关系

SSL VPN 是应用场景，TLS/TLCP 是承载它的安全协议；国密 SSL VPN 使用的是 TLCP。

  • SSL VPN：一种远程接入方案，客户端通过 TLS/TLCP 与服务端建立加密隧道，再在隧道内传输网络流量。SSL VPN 网关通常同时支持国际算法和国密算法两套协议栈。

  • TLS：IETF 标准的传输层安全协议，常见版本 TLS 1.2（记录版本 0x0303）、TLS 1.3（记录版本 0x0303，握手加密）。

  • TLCP：Transport Layer Cryptography Protocol，国密传输层密码协议，结构上参考 TLS 1.1，但记录版本使用自己的 0x0101，密码算法使用 SM2/SM3/SM4。

标准体系

GM/T 0024 与 GB/T 38636 的关系：前者是 SSL VPN 行业规范，后者是更完整的国家标准；两者在套件代码、握手消息上高度一致，具体实现（GmSSL、Tongsuo、各厂商网关）可能有细节差异。分析抓包时以实际字节为准。

国密算法

双证书体系：

  • 签名证书：KeyUsage = digitalSignature，私钥用于签名（ServerKeyExchange、CertificateVerify）。

  • 加密证书：KeyUsage = keyEncipherment / dataEncipherment，公钥用于 SM2 加密预主密钥（ECC）或作为 SM2 密钥交换的静态公钥（ECDHE）。

  • 服务端 Certificate 消息通常按 签名证书、加密证书、CA 证书 的顺序排列；客户端在双向认证时也发送自己的双证书。

密钥交换算法标识

读取位置：ServerHello 的 cipher_suite 字段（2 字节）。

认证方式

认证方式看 CertificateRequest，不看密钥交换算法。

  • CertificateRequest（类型 13）：服务端要求客户端提供证书。

  • 客户端 Certificate（类型 11）：客户端发送自己的证书链（TLCP 为双证书）。

  • CertificateVerify（类型 15）：客户端用签名证书私钥对握手 transcript 签名，证明自己持有私钥。

常见误解：

  • “ECDHE 就是单向认证” —— 错。ECDHE 只是密钥交换方式，认证方式可以单向也可以双向。

  • “ECC 就是双向认证” —— 错。ECC 也可以单向认证。

  • “有 Certificate 就是双向认证” —— 不准确。双向认证的关键是服务端发 CertificateRequest，并且客户端发 Certificate + CertificateVerify。

套件协商

  • ClientHello：客户端发送支持的套件列表、client_random、session ID、扩展。

  • ServerHello：服务端选择一个套件，返回 server_random、session ID。

  • 如果没有共同套件，握手失败（Alert）。

  • 协商结果决定后续所有密钥交换和记录层格式。

  • 降级攻击：攻击者试图让双方选择弱套件/低版本；Finished 的 transcript 校验可以检测部分篡改，但具体防护取决于实现和版本。

抓包字段：

  • Wireshark：tls.handshake.ciphersuite（ServerHello）。

  • 原始字节：ServerHello 消息体中，版本(2) + random(32) + session_id_len(1) + session_id + cipher_suite(2) + compression(1) + extensions。

三、证书与身份认证

双证书体系

TLCP 使用签名证书和加密证书两本证书，分别负责签名和加密/密钥交换。

证书 KeyUsage 私钥用途 公钥用途
签名证书 digitalSignature ServerKeyExchange 签名、CertificateVerify 验签
加密证书 keyEncipherment / dataEncipherment 解密 ClientKeyExchange（ECC）、SM2 密钥交换静态私钥（ECDHE） 加密预主密钥、密钥交换

Certificate 消息中的顺序（常见实现）：

常见错误：

  • 用签名证书私钥解密 ECC 的 ClientKeyExchange → 失败。

  • 用加密证书公钥验 ServerKeyExchange 签名 → 失败。

  • 把两本证书的顺序弄反 → 客户端/服务端证书校验失败。

证书链与信任

  • 证书链：根 CA → 中间 CA → 终端证书。

  • 客户端验证服务端证书链：签名、有效期、主机名、KeyUsage、basicConstraints 等。

  • 双向认证时，服务端也验证客户端证书链。

  • 常见问题：自签名证书、证书过期、链不完整、主机名不匹配、KeyUsage 不允许目标用途。

延伸：证书吊销检查（CRL/OCSP）、证书固定（pinning）、名称约束（name constraints）。

双向认证

服务端发 CertificateRequest，客户端回 Certificate + CertificateVerify，就是双向认证。

CertificateRequest 内容：

  • certificate_types：客户端可用的证书类型；

  • supported_signature_algorithms：签名算法；

  • certificate_authorities：可接受的 CA 列表。

客户端响应：

  1. Certificate：客户端双证书（签名证书 + 加密证书）。

  2. ClientKeyExchange：按套件类型发送 SM2 密文或临时公钥。

  3. CertificateVerify：用客户端签名证书私钥对握手 transcript 签名。

服务端验证

  • 验证客户端证书链；

  • 验证 CertificateVerify 签名；

  • 确认客户端持有签名私钥。

SSL VPN 场景：双向认证常用于客户端准入控制，客户端证书作为身份凭证。

证书校验与中间人

不校验证书，就可能被中间人攻击；双向认证场景下，完整 MITM 需要两端都放松校验或攻击者拥有合法客户端证书。

  • 客户端不校验服务端证书：攻击者可以用自己的证书和临时密钥冒充服务端，客户端会把预主密钥加密给攻击者（ECC）或与攻击者协商密钥（ECDHE）。

  • 服务端不校验客户端证书：攻击者可以冒充客户端接入。

  • 双向认证：攻击者要同时冒充服务端和客户端；如果只放松一端，完整 MITM 可能失败。

  • 防护：证书链校验、主机名校验、证书固定、CRL/OCSP、告警监控。

常见证书问题

问题 表现 影响
自签名证书 链校验失败 客户端拒绝连接
证书过期 有效期校验失败 连接失败
KeyUsage 不匹配 签名/加密用途不允许 握手失败或安全策略拒绝
证书链不完整 找不到签发者 校验失败
签名/加密证书顺序颠倒 用错证书 解密/验签失败
曲线不匹配 不是 curveSM2 密钥交换失败
